# AE2 WCWT 性能与崩溃风险审计报告

- 日期：2026-11-06
- 对象：`main` 分支，提交 `d6000ef`（v1.3.11 发布）
- 范围：`src/main/java` 全部约 3.4 万行 Java，分五个区域（服务端菜单与宿主、网络数据包、客户端界面、mixin 与工具包、兼容层与拉取服务）逐文件通读。
- 方法：纯静态阅读。本机没有 JDK，未编译、未运行、未跑单元测试。每条发现的引用行号都由我在源码中逐条复核；涉及外部 API 行为的判断，对照了 AE2 `neoforge/v19.2.17` 与 NeoForge `1.21.x` 的源码（见各条“依据”）。
- 严重度口径：
  - 崩溃-高：正常玩家可触发的客户端或服务端崩溃、启动失败。
  - 崩溃-中：依赖第三方版本变动或少见数据才触发，但一旦触发即硬崩。
  - 崩溃-低：仅发送方被断开、仅记日志、或实践中几乎不可达。
  - 性能-高：服务端主线程秒级卡顿，或客户端帧率明显下降。
  - 性能-中：随网络规模线性放大的每 tick / 每帧重复工作。
  - 性能-低：常数级浪费，累积后可感知。

历史 issue 的两个主要根因（可选模组类引用、工具包宿主定位）在本次审计中仍是最重的两条（C-1 与 S-1），和已修的 #39、#26、#25 属同一家族。

## 2. 崩溃风险

### C-1 ｜高｜Create 的 `BasinRecipe` 无门控引用

位置：
- [WcwtRecipeTransferHandler.java:317](../../src/main/java/com/lhy/wcwt/compat/jei/WcwtRecipeTransferHandler.java:317) 与 [:339](../../src/main/java/com/lhy/wcwt/compat/jei/WcwtRecipeTransferHandler.java:339)，`recipe instanceof BasinRecipe basinRecipe`
- [WcwtEmiRecipeHandler.java:502](../../src/main/java/com/lhy/wcwt/compat/emi/WcwtEmiRecipeHandler.java:502) 与 [:567](../../src/main/java/com/lhy/wcwt/compat/emi/WcwtEmiRecipeHandler.java:567)

机制：全仓库没有任何 `ModList.get().isLoaded("create")`，`neoforge.mods.toml` 也未声明 create。类本身能通过校验，但 JVM 在执行 `instanceof` 且对象非 null 时必须解析 `BasinRecipe`，Create 缺失即抛 `NoClassDefFoundError`。四处都在“显示槽位无法转换成 GenericStack”之后的回退分支：JEI 的 `collectProcessingInputs` / `collectProcessingOutputs`，EMI 的 `collectEncodingInputs` / `collectEncodingOutputs`。

触发场景：未装 Create 的整合包里，对任何输入或输出全部不是物品、流体的处理配方点 JEI 的“+”或 EMI 填充按钮。最典型的是只装 Mekanism、未装 Applied Mekanistics 时的化学品配方（化学灌注器、电解分离器、溶解室等）。`NoClassDefFoundError` 是 `Error`，不会被 JEI 对 `RuntimeException` 的捕获接住，顺着 `Screen` 事件处理器一路抛到崩溃报告。悬停预览（`doTransfer=false`）不触发。

置信度：很可能。`instanceof` 解析语义确定；“崩溃而非仅报错”依赖 JEI 的捕获范围（凭记忆是 `RuntimeException`，未能核对源码），即使被捕获，该配方也会永久无法传输。

修复：把 Basin 回退逻辑移进 `isLoaded("create")` 门控的嵌套 `Impl` 类（与 `AppliedMekanisticsCompat` 同一模式），并在 mods.toml 把 create 声明为 optional。

### C-2 ｜中｜Better Combat mixin 硬绑定字节码形状

位置：[WcwtBetterCombatMixin.java:17](../../src/main/java/com/lhy/wcwt/mixin/WcwtBetterCombatMixin.java:17)，`@Redirect(... require = 4, allow = 4)`；[wcwt.mixins.json](../../src/main/resources/wcwt.mixins.json) `required: true`、`defaultRequire: 1`。

机制：`@Pseudo` 只在 Better Combat 不存在时跳过。只要 BC 存在而 `swapHandAttributes` 里 `NonNullList.set` 的调用次数不是恰好 4 次，Mixin 应用失败，游戏启动即崩。作者的离线验证脚本（`src/test/bettercombat/`）只针对 BC 2.4.0 一个版本。

触发场景：整合包升级或降级 Better Combat。

置信度：确定（机制），版本是否会变属“可能”。

修复：改为 `require = 0` 并在未命中时打一次警告降级；或在 mods.toml 给 bettercombat 加版本区间。

### C-3 ｜中｜EMI mixin 注入非 API 内部类

位置：[WcwtEmiRecipeDisplayMixin.java:15](../../src/main/java/com/lhy/wcwt/mixin/WcwtEmiRecipeDisplayMixin.java:15)，目标 `dev.emi.emi.screen.RecipeDisplay#getWidgets(IIII)`，并直接读公共字段 `WidgetGroup.widgets`。

机制：`RecipeDisplay`、`WidgetGroup` 都不是 EMI 公开 API。`@Pseudo` 只保护“类不存在”；方法签名或字段可见性一变，`defaultRequire: 1` 会在打开配方页时硬崩，字段改私有则 `IllegalAccessError`。

修复：改用 EMI 公开扩展点（`EmiRecipeHandler.render` 已在用，或 recipe decorator），至少 `require = 0` 加版本区间。

### C-4 ｜低｜七个数据包的枚举解码无范围检查

位置：
- [CellWorkbenchActionPacket.java:30](../../src/main/java/com/lhy/wcwt/network/CellWorkbenchActionPacket.java:30)
- [DirectionChangePacket.java:50](../../src/main/java/com/lhy/wcwt/network/DirectionChangePacket.java:50)
- [EncodePatternPacket.java:23](../../src/main/java/com/lhy/wcwt/network/EncodePatternPacket.java:23)
- [ExtendedUIPacket.java:21](../../src/main/java/com/lhy/wcwt/network/ExtendedUIPacket.java:21)
- [PatternEncodingModePacket.java:18](../../src/main/java/com/lhy/wcwt/network/PatternEncodingModePacket.java:18)
- [PatternMultiplierPacket.java:28](../../src/main/java/com/lhy/wcwt/network/PatternMultiplierPacket.java:28)
- [PatternManagementActionPacket.java:57](../../src/main/java/com/lhy/wcwt/network/PatternManagementActionPacket.java:57) 与 :69

机制：解码在 netty 线程进行，`ArrayIndexOutOfBoundsException` 会让该连接以“Internal Exception”断开。仓库里已经有 `WcwtPacketLimits.readEnum`，只是没有统一使用。`PatternManagementActionPacket` 还在每次编解码时 `new` 一个 idMapper。

触发：篡改客户端，或客户端与服务端模组版本不一致时枚举新增常量。只影响发送方自身。

修复：统一改用 `WcwtPacketLimits.readEnum`。

### C-5 ｜低｜供应器列表包总大小无上限

位置：[PatternProviderListPacket.java:48](../../src/main/java/com/lhy/wcwt/network/PatternProviderListPacket.java:48)（`ByteBufCodecs.list()` 无上限）、[:196](../../src/main/java/com/lhy/wcwt/network/PatternProviderListPacket.java:196)（仅按单个供应器截断）。

机制：`maxSyncedSlotsPerProvider` 只限制单个供应器，不限制条目总数和字节数；每个编码样板连组件约 200 到 500 字节，整表发送。原版对出站包有大小上限，超限在 netty 线程抛异常并断开该玩家，重进后一打开面板就会复现。该包在 `broadcastChanges`、上传通知、管理动作和请求四处发送。

触发：数万张样板的大型存档正常打开样板管理区。置信度：可能（阈值依赖原版常量）。

修复：按累计条目数或估算字节数设全局上限并告警截断，长期改分页或增量同步。

### C-6 ｜低｜`isCellSlotEnabled` 未判空

位置：[WirelessComprehensiveWorkTerminalMenu.java:4122](../../src/main/java/com/lhy/wcwt/menu/WirelessComprehensiveWorkTerminalMenu.java:4122)。

机制：AE2 的 `ICellWorkbenchItem.getConfigInventory(ItemStack)` 标注 `@Nullable`，同文件其它四处调用都判了空，唯独这里直接 `.size()`。该方法由客户端高级编码面板在渲染与点击时调用。

触发：第三方“可编辑但无过滤配置”的元件放入元件槽并打开高级编码面板。置信度：可能。

### C-7 ｜低｜倍增器溢出检查自身溢出

位置：[WirelessComprehensiveWorkTerminalMenu.java:4296](../../src/main/java/com/lhy/wcwt/menu/WirelessComprehensiveWorkTerminalMenu.java:4296)，`stack.amount() * scale > maxAmount`。

机制：乘积回绕成负数后检查通过，负数 `GenericStack` 交给 AE2 编码会抛 `IllegalArgumentException`。依据 NeoForge 源码，`enqueueWork` 内的异常只记日志（`NetworkRegistry.guard`），不踢人不宕服，但本次请求里已处理的前几张样板会被部分改写。

触发：缓存区存在数量约 1.8e18 的样板，只能靠 NBT 编辑得到。修复：改为 `amount > maxAmount / scale`。

### C-8 ｜低｜`WcwtJeiBookmarkKeys` 硬引用 JEI 且无门控

位置：[WcwtJeiBookmarkKeys.java:5](../../src/main/java/com/lhy/wcwt/compat/jei/WcwtJeiBookmarkKeys.java:5) 起直接 import JEI API，静态字段类型 `IJeiRuntime`；[ModClientSetup.java:61](../../src/main/java/com/lhy/wcwt/client/ModClientSetup.java:61) 在每次按键时无条件调用 `isSearchFieldFocused()`。`neoforge.mods.toml` 未声明 jei。

机制：现在能跑是因为 HotSpot 懒解析加 `runtime == null` 提前返回。同一个 Screen 在 2055 行附近对另一个 JEI 调用却做了 `isLoaded("jei")` 门控，不一致。任何让校验器需要加载 JEI 类型的改动（`checkcast`、JEI 具体类参与栈帧合并）都会让无 JEI 的玩家每次按键 `NoClassDefFoundError`。

修复：调用前加 `isLoaded("jei")`，或把 JEI 类型成员移入嵌套类。

### C-9 ｜低｜`decodePattern` 传入可能为 null 的 `level`

位置：[ResonatingLightningPatternCodingPanel.java:409](../../src/main/java/com/lhy/wcwt/client/gui/panels/ResonatingLightningPatternCodingPanel.java:409)；[WirelessComprehensiveWorkTerminalScreen.java:4159](../../src/main/java/com/lhy/wcwt/client/WirelessComprehensiveWorkTerminalScreen.java:4159)（`Objects.requireNonNull`）。

其余同类调用都判了 `level != null`。实践中屏幕存在时 `level` 不会为 null，仅一致性风险。

### C-10 ｜低（内存）｜远程菜单会话表断线不清理

位置：[WcwtRemoteMenuAccess.java:20](../../src/main/java/com/lhy/wcwt/helpers/WcwtRemoteMenuAccess.java:20)、[:43](../../src/main/java/com/lhy/wcwt/helpers/WcwtRemoteMenuAccess.java:43)；[WcwtMenuEvents.java:14](../../src/main/java/com/lhy/wcwt/WcwtMenuEvents.java:14) 只在 `PlayerContainerEvent.Close` 清理。

机制：原版断线流程不调用 `closeContainer`，死亡重生也不关闭旧容器，所以 `Close` 不触发。`Session` 强引用 `AbstractContainerMenu`（间接引用已离线的 `ServerPlayer`）和 `BlockEntity`（引用 `ServerLevel`）。单人游戏在远程菜单打开时崩溃回主菜单再进另一个世界，旧世界会被钉住。专用服务器上泄漏量以离线 UUID 数为界。

修复：在 `PlayerLoggedOutEvent` 与 `ServerStoppingEvent` 清理；或只存坐标不存对象。

### C-11 ｜低｜`instanceof` JEI `library` 内部类

位置：[WcwtRecipeTransferHandler.java:29](../../src/main/java/com/lhy/wcwt/compat/jei/WcwtRecipeTransferHandler.java:29)、[:508](../../src/main/java/com/lhy/wcwt/compat/jei/WcwtRecipeTransferHandler.java:508)，`mezz.jei.library.plugins.jei.tags.ITagInfoRecipe` 与 `...info.IngredientInfoRecipe`。

JEI 移动或删除这两个类时，WCWT 打开后任何 JEI 配方预览都会 `NoClassDefFoundError`。当前 pinned 的 JEI 版本存在这两个类。建议改为按类名反射判断。

## 3. 服务端性能

### S-1 ｜高｜工具包网络工具定位器每次 `locateItem` 构造完整终端宿主

位置：
- [WcwtToolkitNetworkToolLocator.java:47](../../src/main/java/com/lhy/wcwt/menu/locator/WcwtToolkitNetworkToolLocator.java:47)，`wcwtItem.getMenuHost(player, terminalLocator, null)`，只为了读工具包里的一格
- [WirelessComprehensiveWorkTerminalMenuHost.java:254](../../src/main/java/com/lhy/wcwt/helpers/WirelessComprehensiveWorkTerminalMenuHost.java:254) 到 :284 构造函数：`PatternEncodingLogic.readFromNBT`、两个 27 格 `ConfigInventory.readFromChildTag`、十余次组件读取、`consumePendingExtendedUi(player)`、末尾 `refreshMenuSyncState()`
- [WcwtToolkitNetworkToolSupport.java:118](../../src/main/java/com/lhy/wcwt/helpers/WcwtToolkitNetworkToolSupport.java:118)，`createHostFromTerminal` 对背包和 Curios 里每个终端各构造一次

依据（AE2 19.2.17 源码）：`AEBaseMenu.broadcastChanges` 每 tick 调 `itemMenuHost.isValid()`，`ItemMenuHost.isValid()` 走 `getItemStack()`，即 `locator.locateItem(player)`；`ToolboxMenu.tick()` 对工具箱宿主同样每 tick `isValid()`。`PatternProviderLogic.getTerminalGroup()` 与 WAP 扫描都不便宜。

机制：工具包里放有网络工具时，`WcwtNetworkToolItemMixin` 让 `findNetworkToolInv` 返回 `WcwtToolkitNetworkToolMenuHost`，其定位器就是上面这个。于是任何带工具箱的 AE2 菜单（ME 箱、总线、接口、样板供应器）以及 WCWT 自身打开期间，服务端每 tick 至少构造并丢弃一到两个完整终端宿主，伴随 NBT 解析和 WAP 测距。多玩家线性叠加。副作用：`consumePendingExtendedUi` 每次都会删除玩家持久数据里的 `pending_extended_ui`，详见第 4 节 F-4。

置信度：确定。

修复：`locateItem` 直接用 `WcwtToolkitStore.items(player, null)`（服务端本就是按玩家共享的同一个库存）取格子；`createHostFromTerminal` 同理。`consumePendingExtendedUi` 移到真正打开菜单的路径。

### S-2 ｜高｜锤子拉取的复杂度随整个 ME 网络放大

位置：
- [WcwtMeIngredientExtraction.java:83](../../src/main/java/com/lhy/wcwt/pull/WcwtMeIngredientExtraction.java:83)，每个配料一次 `storage.getAvailableStacks()`、整表排序、每个 key 做 `matches(wide)`
- [WcwtTerminalPullService.java:93](../../src/main/java/com/lhy/wcwt/pull/WcwtTerminalPullService.java:93) 与 [:285](../../src/main/java/com/lhy/wcwt/pull/WcwtTerminalPullService.java:285) 到 :303，`maxTransfer` 时把全网装入 `availableByKey`，最多 64 轮
- [WcwtTerminalPullService.java:308](../../src/main/java/com/lhy/wcwt/pull/WcwtTerminalPullService.java:308)，每轮 `new LinkedHashMap<>(availableByKey)` 复制整张表
- [WcwtMeIngredientExtraction.java:127](../../src/main/java/com/lhy/wcwt/pull/WcwtMeIngredientExtraction.java:127) 与 :142，每个配料对整张 `remaining` 遍历两次

依据（AE2 源码）：`MEStorage.getAvailableStacks()` 默认新建 `KeyCounter` 并遍历全部已挂载存储；WCWT 自己的 `TimedStorage` 包装（[MenuHost:377](../../src/main/java/com/lhy/wcwt/helpers/WirelessComprehensiveWorkTerminalMenuHost.java:377)）即使命中 5 tick 缓存也会 `copyCounter` 全量复制。

## 5. 顺带发现的功能性缺陷

这些不属于性能或崩溃，但都是真实缺陷，建议在大修时一并处理。

- F-1 槽位保护 mixin 从未生效：[WcwtMenuProtectionMixin.java:30](../../src/main/java/com/lhy/wcwt/mixin/WcwtMenuProtectionMixin.java:30) 用小写 `contains("wcwt_pattern_cache")` 等匹配，而注册 id 是大写 `WCWT_PATTERN_CACHE`。AE2 19.2.17 的 `SlotSemantic` 是 record，`toString()` 输出含大写 id，所以四类 WCWT 专属槽从未被标为非玩家侧。
- F-2 拉取物品可能丢失：[WcwtTerminalPullService.java:158](../../src/main/java/com/lhy/wcwt/pull/WcwtTerminalPullService.java:158) 对 `StorageHelper.poweredInsert` 的返回值未检查，网络无电或存储满时已提取的剩余物品直接消失。
- F-3 反射失败静默降级：[WcwtReflect.java:137](../../src/main/java/com/lhy/wcwt/compat/reflect/WcwtReflect.java:137) 到 :212 的 `invoke` / `run` / `readField` / `writeField` 捕获 `Throwable` 后只 `logDebug`（默认关闭），没有 `warnOnce`。[NeoFavoriteItemsCompat.java:24](../../src/main/java/com/lhy/wcwt/compat/NeoFavoriteItemsCompat.java:24) 失败时 `orElse(true)` 会静默阻止拾取方块；磁力设置写入失败也无任何日志。与 README“只警告一次并降级”的承诺不符。
- F-4 `consumePendingExtendedUi` 有副作用地放在宿主构造函数里（[MenuHost:276](../../src/main/java/com/lhy/wcwt/helpers/WirelessComprehensiveWorkTerminalMenuHost.java:276) → :1272），S-1 的定位器路径每 tick 构造宿主时都会把玩家持久数据里的 `pending_extended_ui` 删掉，快捷键请求打开的扩展面板可能被“吃掉”。
- F-5 空壳栈：[WcwtInventoryMixin.java:35](../../src/main/java/com/lhy/wcwt/mixin/WcwtInventoryMixin.java:35) 把数量归零但非 `EMPTY` 的栈写回工具包格，与同文件 `dropSelected` 的归一化不一致；[WcwtToolkitHotbarState.java:251](../../src/main/java/com/lhy/wcwt/helpers/WcwtToolkitHotbarState.java:251) 先 `shrink` 再取 `getItem()` 计统计，永远记在 `minecraft:air` 上，且不调用 `player.take` 没有拾取动画。
- F-6 EAEP 异常中断编码：[PlusPatternUploadApi.java:248](../../src/main/java/com/lhy/wcwt/compat/plus/PlusPatternUploadApi.java:248) 刻意原样重抛 EAEP 的异常，而菜单在 :2178 已把样板放进输出槽、:2254 的上传无 try/catch。异常被 `enqueueWork` 记日志后，任务停在“样板已入槽、未上传、未补空白样板、未广播”的中间状态。
- F-7 版本错配时的重复 `LinkageError`：`JecSearchCompat.Impl.contains` 与 `Ae2JeiIntegrationCompat.Impl.convert` 在目标 API 变动时每次调用都新建并吞掉 `NoSuchMethodError`，前者在搜索过滤每条目调用，后者在 JEI 每 tick 预览每槽调用，没有负缓存。

## 6. 修复优先级建议

第一批（崩溃与服务端卡顿，建议先做）：
1. C-1：Create 引用移入门控嵌套类，mods.toml 声明 optional。
2. S-1 加 F-4：定位器改读共享工具包库存；`consumePendingExtendedUi` 移出构造函数。
3. S-2：拉取服务只取一次快照、候选小集合、备选总数硬上限、每玩家节流。
4. S-4 加 S-5：预计算排序键；`Request.handle` 校验菜单类型并统一节流；管理动作复用缓存。
5. C-4 加 S-11：统一 `readEnum`；搜索文本限长。
6. C-2 加 C-3：两个第三方 mixin 改 `require = 0` 并加版本区间。

第二批（客户端帧率）：K-1、K-2、K-3、K-4、K-5、K-7、K-8。这几条的共同模式都是“每帧重算只有在输入变化时才会变的东西”，可以用同一套“按输入签名缓存”的办法处理。

第三批：其余低项与第 5 节的功能缺陷。

通用建议：
- 所有数据包处理统一加一个每玩家节流工具（按 tick 计数即可），现在只有两个包有。
- 用现成的 `-Dwcwt.debug.perf=true` 在大网络存档上实测 S-2、S-4、K-1、K-8 的绝对耗时，作为修复前后的对比基线。
- 对 Better Combat、EMI 这类依赖内部实现的 mixin，加 `MixinConfigPlugin` 按版本启用。
